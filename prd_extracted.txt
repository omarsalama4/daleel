1. Executive Summary
Daleel is a hosted research crawler for the product owner and a small group of invited friends. A user asks a question, optionally provides starting sites, and receives structured findings with source URLs, supporting evidence, relevance labels, crawl coverage, and exports. The system can discover candidate sites from a query, follow relevant links across domains within limits, and use user-authorized browser sessions where sign-in is required. [Decision]
A user can turn any query into a proposed workflow. It describes where to look, what to collect, how to judge relevance, what evidence to retain, how to deduplicate, and whether detail-page enrichment is needed. The AI Engineer opportunity search is the reference workflow, not the only supported task. [Decision]
Daleel combines language-model reasoning with deterministic orchestration and browser execution. The orchestrator owns permissions, queue state, retries, limits, AI model usage caps, and stop conditions. Agents can plan and extract through controlled tools; they cannot grant themselves new scope or override policy. [Reference PRD]
The first release is a private hosted beta with one personal workspace per invited user and a SaaS-ready foundation. Neon Postgres, Neon Managed Better Auth, Neon Object Storage, and Google Cloud Run are selected beta services. [Decision] Billing and public launch remain out of scope. Search, model, email, and observability providers remain replaceable recommendations; the AI model usage caps are approved. [Decision]
2. Product Vision
Help people turn a natural-language question into a bounded, repeatable web research workflow that finds useful information, verifies it against source evidence, and preserves the automation for reuse.
Users should be able to see what the system planned, which sources it reached, what it extracted, why results were considered relevant, and what it could not complete. [Brief]
3. Problem Statement
Research across many websites is repetitive. Users search, open pages, collect details into notes or spreadsheets, revisit the same sites, and rebuild scripts when page structure changes. One-off scrapers can lose provenance, silently omit inaccessible pages, or return unstructured output.
An unconstrained agent can over-crawl, produce unsupported claims, misuse an authenticated session, or fail without a useful explanation. Daleel addresses these risks through explicit scope, deterministic run limits, versioned recipes, structured extraction, evidence retention, and partial-result reporting. [Proposal]

17.1 Human-in-the-loop role and approval model [Decision]
Human-in-the-loop is Daleel’s policy, access, and quality-control layer. People authorize scope, supply authenticated access themselves, review generated recipes when required, and correct ambiguous findings. Users do not need to approve every page fetch.
Approval mode: before execution, the user reviews and may edit the interpreted query, target domains, fields, relevance setting, crawl limits, AI model usage caps, and proposed recipe, then approves the run. A new or changed recipe must be previewed and approved before activation. The user signs into the target site and completes MFA in the browser; Daleel reuses only that user’s authorized session. The user can pause, resume, cancel, annotate, or correct results.
Autonomous mode: run the query without waiting for a Save workflow action. The user may authorize discovery and crawling of public domains reached through links within the configured 20-domain Standard envelope and other run limits, without per-domain approval. Remain within the user's initial query scope, AI model usage caps, authorized sessions, and approved recipe versions. Pause or skip when scope or limits would expand, access requires user action, a barrier appears, recipe drift lowers confidence, a material ambiguity changes the result, an interaction is not confidently read-only, or a budget boundary is reached. [Decision]
Autonomous mode is bounded delegation, not unrestricted access. Daleel never solves or bypasses CAPTCHA/MFA/bot detection, reauthenticates as the user, expands scope by itself, or performs write actions. A human must resolve access barriers through the normal site flow or end the run.
Feedback: users may mark a result relevant, irrelevant, incomplete, or incorrect and provide a correction. Feedback is tied to the workspace, run, and workflow/recipe version. It may inform a proposed ranking or recipe revision, but never silently changes an approved workflow or prior results.
Roles: each beta user is the Owner of a personal workspace and controls its content, AI processing policy, budgets, and sessions. The Platform Operator administers invitations and may inspect private run content for support under an internal, admin-only access audit; the operator cannot inspect raw session secrets or override the Owner's authenticated-content AI policy. Explicit sharing grants access only to selected findings or recipes, never to a session or private run history. [Decision]
17.2 Agent pattern selection and execution model
Plan-and-Execute is the primary run pattern. A Planner decomposes a user query into typed discovery, crawl, extraction, enrichment, validation, and reporting tasks. It emits a schema-validated dependency DAG with declared inputs, outputs, scope, and estimated resource use. The deterministic scheduler owns execution, concurrency, budgets, retries, and stop conditions; LangGraph provides typed state, durable checkpoints, and resumable interrupts for long-running work. [Proposal]
ReWOO and LLMCompiler influence planning and scheduling: resolve the known plan and dependencies before dispatch, then run independent domains, pages, and extraction tasks concurrently. Join dependent tasks only when their inputs are ready. Per-domain rate limits, host concurrency, total run limits, and provider caps always constrain parallel work. Keep model planning separate from browser side effects. [Proposal]
Use ReAct only as a bounded browser interaction loop when permitted static retrieval, sitemaps, and documented endpoints cannot provide the page content. Give it a narrow set of read-only browser tools, a step limit, and a time limit. Conditional routing should prefer the least interactive permitted method and escalate to browser rendering only when needed. If login expires or MFA, CAPTCHA, bot detection, or another access barrier appears, pause for the user or stop; never automate bypass. [Proposal]
Use structured Pydantic outputs for plans, task results, extracted records, and completion reports. Each surfaced field must point to evidence such as a source URL, retrieval time, and supporting text or artifact reference. Evidence retrieval supplies source-backed context to ranking and final answers; unsupported or conflicting fields are marked uncertain instead of being filled by inference. [Proposal]
Reflection is a targeted quality check after extraction: verify required fields, schema validity, evidence coverage, contradictions, and task completeness. Permit at most one focused correction pass within the existing retry and spend limits, then return the uncertainty or gap. Do not run open-ended self-critique loops. [Proposal]
Reflexion-style cross-run learning is limited to versioned recipes, selectors, drift notes, and user feedback. Reuse only an approved recipe version inside its saved scope. Suggestions from failures or feedback create a proposed revision for review; they never change scope, credentials, or an active approved recipe silently. [Proposal]
Capability progression: establish Plan-and-Execute with LangGraph state and evidence first; add ReWOO/LLMCompiler-inspired dependency scheduling and bounded parallelism next; then add targeted reflection and reviewed recipe memory. ReAct remains a page-level fallback, not the top-level run controller. This sequence keeps the system useful for arbitrary query workflows while limiting agent calls and making failures inspectable. [Proposal]

23. High-Level Technical Architecture
The hosted system comprises a FastAPI control plane, LangGraph workflow runtime, PostgreSQL system of record and durable queue, isolated Playwright workers, replaceable search/model adapters, and evidence storage. See 23.1 for the recommended private-beta stack and its free-tier limitations. [Proposal]
Typical flow: User UI → Query Planner → Policy/Budget Gate → Durable Orchestrator → Search/Discovery Tasks → Isolated Fetch/Browser Workers → Extraction and Validation → Results/Evidence Store → Report and Exports.
The Orchestrator is the source of truth for task state, budgets, retries, and permissions. The model plans and extracts; it does not act as the workflow engine. [Proposal]
23.1 Recommended private-beta technology stack [Proposal]
Application API: Python 3.12, FastAPI, and Pydantic v2. Use typed request/response contracts and schema validation at every agent boundary.
Agent framework: LangGraph for a stateful, checkpointed workflow graph with interrupt/resume at human approval gates. The deterministic orchestration layer owns permissions, scope, retries, budgets, and stop conditions; model agents propose and extract but do not control infrastructure.
Product identity and invitations: Neon Managed Better Auth for accounts and personal workspace ownership. [Decision] Resend Free is the proposed transactional invitation and notification email service; queue or report when its quota is exhausted and never silently incur overage. [Proposal]
System of record and queue: Neon Postgres for the invite-only beta, with SQLAlchemy and Alembic migrations. Implement the queue as application-owned PostgreSQL run/task tables with leases, fencing tokens, idempotency keys, bounded retries, and SKIP LOCKED claiming; keep a queue adapter boundary. Use Neon pooled runtime connections and reconnect after scale-to-zero. Each on-demand Cloud Run Job claims only its run's tasks; recovery scans reclaim expired leases. [Decision] Neon Object Storage holds evidence artifacts behind a replaceable adapter. [Decision] Enforce personal-workspace isolation in application authorization and database Row Level Security, with a separately audited platform-operator access path.
Browser and reusable RPA: Playwright for Python in isolated workers launched by an on-demand Cloud Run Job per run. Store versioned, structured recipes and inspectable/exportable Playwright actions; keep credentials and session state out of recipes. Permit discovered public domains inside the query envelope and configured domain limit. Restrict workers to likely read-only interactions, job-scoped session references, and run budgets; pause or skip ambiguous controls.
AI providers: Groq as the primary inference adapter and OpenRouter Free models as a quota-limited secondary route. Keep both behind a provider interface. Do not silently fall back to a paid model; if a free quota is exhausted, queue or stop with a clear partial-run reason.
Search and discovery: Tavily Search as the initial provider. Its current free plan includes 1,000 API credits per month without a credit card; credit use varies by endpoint. Disable paid upgrades by default and stop or wait when the included quota is exhausted.
Hosting: Google Cloud Run for the FastAPI service and isolated browser/worker containers, with a region selected near users and required target sites. Cloud Run has a monthly free usage allowance, but a billing account is required and overage, networking, image storage, and sustained browser work can incur charges. Use Cloud billing alerts and low worker concurrency; these infrastructure costs are outside the AI model usage caps. [Decision]
Tracing and observability: OpenTelemetry Python instrumentation for FastAPI and manual spans across planning, queue wait, browser fetch, extraction, provider calls, and persistence; propagate trace and run IDs across workers. Use Langfuse Cloud Hobby for agent traces and token/cost inspection (currently 50,000 units/month, 30 days of history, and two users), plus Cloud Run logs/metrics. Never send passwords, cookies, session state, raw page HTML, or unnecessary personal data to traces.
CI/CD: GitHub Actions for pull-request linting, type checks, tests, dependency/security checks, container builds, and controlled deployment to Cloud Run. Use short-lived workload identity federation/OIDC for cloud deployment instead of long-lived service-account keys. GitHub Free currently includes 2,000 hosted-runner minutes/month for private repositories.
Beta quota behavior: Groq limits vary by model and account; OpenRouter Free currently lists 25+ free models and 50 requests/day. Treat all free quotas and model availability as provider-controlled. The app’s $0.25/run and $5/workspace/month defaults are local estimated-usage guardrails; owners can adjust them, and paid model calls require explicit enablement.
Hosted free-tier caveats: Neon Free currently includes 100 CU-hours per project/month, 0.5 GB database storage, 10 branches, and up to 2 CU autoscaling; its Object Storage allowance is currently 5 GB per project. Reconnect after database suspension and avoid frequent queue polling. Treat provider limits as subject to change and monitor usage. The app's beta evidence ceilings are 500 MB per workspace and 4 GB overall, leaving headroom under the current provider allowance. Research results remain until manually deleted; Langfuse's free-cloud trace history has separate retention.

23.3 Data and telemetry boundary [Proposal]
Product findings and evidence follow the product’s manual-deletion rule. Operational traces have a separate provider retention window and contain only minimized, redacted metadata. A user deletion request must also remove linked trace records where the observability API permits; trace storage is not the system of record.
23.4 Run execution, recovery, and accounting [Decision]
A FastAPI request creates a run and a typed dependency DAG in Neon Postgres. An on-demand Cloud Run Job is launched for that run; its bounded workers claim only ready tasks for that run with PostgreSQL leases, fencing tokens, and idempotency keys. Neon run/task rows are authoritative. LangGraph checkpoints preserve agent state and human interrupts but do not replace the task ledger.
A worker heartbeats its lease and commits task result, evidence pointer, and attempt status atomically where possible. Expired leases are reclaimed by a recovery sweep; a restarted Job resumes unfinished tasks without reissuing already committed findings. Cancel or pause blocks new claims and lets in-flight tasks settle safely. Every task ends in succeeded, skipped, blocked, failed, or cancelled state. Complete means all discovered in-scope tasks reached an accounted-for terminal state; otherwise the run is Partial or Failed with a clear reason and retained findings.
Reserve estimated AI cost before each model call in a workspace/run ledger and reconcile provider-reported actual usage afterward. Record timed-out attempts because providers may still bill them. The $0.25/run and $5/workspace/month defaults guard AI model usage only. When free search credits end, stop with partial results; paid search stays disabled by default. Set Cloud Run worker concurrency ceilings and Google Cloud billing alerts for infrastructure spend.
23.5 Evidence, retention, and data location [Decision]
Each surfaced factual field stores a source URL, fetched-at time, minimal excerpt or snapshot, and content digest, linked to the extraction and model/prompt/schema versions. Raw page copies are optional. Evidence and results remain until manually deleted. The beta warns at 80% of 500 MB per workspace or 4 GB overall; at a limit it pauses new storage-heavy runs until content is manually deleted or capacity is increased. These evidence limits are separate from the 100 MB Standard per-run download limit.
Choose a hosted region near beta users and disclose where product data is stored; Egypt-only residency is not required. A Workspace Owner decides whether authenticated page content may be sent to hosted AI providers. The Platform Operator cannot override that choice. Operator access to private workspace content is internally audited for platform admins only; raw cookies and session secrets remain inaccessible through the support path.

31.1 Private-beta release gates [Decision]
Use a human-reviewed benchmark covering the AI Engineer opportunity template plus at least one non-job query, public HTML, PDFs, and authenticated interactive pages. Include English and Arabic cases. Every relevant job finding receives a detail-page attempt or a clear incomplete reason; duplicates referring to the same opportunity are grouped with provenance retained.
Provisional gates are at least 90% extracted-field precision and 80% relevant-result recall on the reviewed benchmark; 100% of surfaced factual fields have supporting evidence or are marked unsupported/unknown. There must be zero unauthorized site changes and zero peer-workspace data leaks. Review the thresholds and the benchmark composition using beta evidence before expanding access.
Exercise run crash/restart, lease expiry, cancellation, search-credit exhaustion, AI call timeout, evidence quota, recipe drift, CAPTCHA/MFA barrier, and manual deletion. A run must retain completed findings, show coverage and stop reason, and report actual AI usage plus separate non-AI usage. Verify that operator private-content access is internally audited, raw session secrets stay inaccessible, and each Workspace Owner's authenticated-content AI policy cannot be overridden.
